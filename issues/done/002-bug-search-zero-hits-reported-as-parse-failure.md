# bug: ヒット 0 件と HTML 解析の失敗が同じエラーになる

## 症状（実測 2026-09-15）

特定の検索クエリで次のエラーになる。

```
$ esa search -n 3 '<あるクエリ>'
エラー: 検索結果から記事を抽出できませんでした（HTML 構造が変わった可能性があります）
```

別のクエリでは同じ実行で正常に結果が返るので、**esa の HTML 構造が変わったわけではない**。

## これは退行ではない

リダイレクト方針・後置フラグの検出・TSV の無害化を入れた版と、その直前の HEAD の版で
A-B 比較したところ、**両方とも同じクエリで同じエラー**、別のクエリでは**両方とも成功**した。
これらの変更より前から在る挙動。

## 疑い

「ヒット 0 件」と「HTML の構造が想定と違う」を区別できていない可能性が高い。
どちらも「記事要素が 1 つも取れなかった」として同じ経路に落ちる。

これは jiikko/newrelic-nrql-cli で直したのと同じ形の欠陥:
あちらは NerdGraph の `account: null`（引けなかった）と `results: []`（本当に 0 件）が
どちらも「0 件」rc=0 になっていた。**「取れなかった」と「無かった」を型・経路で分ける**のが解。

## 受け入れ条件

- [ ] 0 件と解析失敗を切り分ける（「0 件でもページに在るもの」= 検索結果のコンテナ要素や
      件数表示を探して判定する）
- [ ] 0 件なら `0 件` を stderr に出して rc=0、解析失敗なら今のエラーで rc=1
- [ ] どちらのケースも HTML の fixture を保存してテストで固定する
- [ ] 判定の根拠となる要素は、実際の esa の HTML を見て確定させる（推測で書かない）


---

## 決着（2026-09-16、v0.1.4）

### 原因: 0 件マーカーが「先頭 32,768 バイト」の窓の外だった

判定の仕組み（`isEmptyResultPage`）は**最初から在った**。マーカーの一覧にも
「見つかりませんでした」が入っていた。効かなかったのは検索範囲が
`body[:min(len(body), 32768)]` に限られていたため。

実測（2026-09-16）:

| 項目 | 値 |
|---|---|
| 0 件ページ全体 | 65,457 バイト |
| `search__no-result` の位置 | 51,532 バイト目 |
| 「見つかりませんでした」の位置 | 51,741 バイト目 |
| 旧実装が見ていた範囲 | 先頭 32,768 バイトまで |

esa の検索結果ページはヘッダ・サイドバー・検索オプションが長く、本文の判定材料が
30KB 以降に来る。ページ長は記事数やチーム設定で変わるので、**窓の大きさをいくつにしても
同じ形で壊れる**。

### 対応

文字列の窓をやめ、**DOM で `class` が `search__no-result` で始まる要素を探す**形にした。
class 名は実レスポンスから確認した（`search__no-result` / `search__no-result-message`）。

```
$ esa search -n 3 '<0 件になるクエリ>'
0 件            # 以前: エラー: 検索結果から記事を抽出できませんでした
$ echo $?
0               # 以前: 1
```

「抽出できませんでした」は、**0 件マーカーも記事リンクも無いとき**だけ出るようになった
（本当に HTML 構造が変わったケース）。

### テスト

- fixture は実際の esa の HTML を貼らず、判定に必要な構造だけを再現した
  （社内の記事名・チーム名を公開リポジトリに持ち込まないため）
- **マーカーの前に 40KB の詰め物を置いてある**。旧実装（先頭 32,768 バイト）に戻す変異で
  red になることを確認済み。窓の大きさを戻す退行をこれで止める
- 「0 件マーカーが無いページを 0 件と誤判定しない」ことも固定（常に true を返す変異で red）

### 分かったこと

issue を書いた時点では「newrelic-nrql-cli と同じく、0 件と取得失敗を型で分けていない」と
推測していたが、**実際は分ける仕組みが在り、観測範囲が足りなかった**。
推測のまま「型で分ける」改修に進んでいたら、既に在る機構を作り直していた。
